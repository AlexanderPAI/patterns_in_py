# TDD

В тестах сервисного слоя по-прежнему есть зависимости от предметной области, потому что мы используем объекты
предметной области для настройки тестовых данных и вызова функций сервисного слоя.

Для того, чтобы иметь полностью не связанный с предметной областью сервисный слой, нужно переписать его API, чтобы
работать с примитивами.

Например:

Зависимый слой
```python
# зависит от OrderLine
def allocate(line: OrderLine, repo: AbstractRepository, session) -> str:
    ...
```

Вот так он мог бы выглядеть
```python
def allocate(orderid: str, sku: str, qty: int, repo: AbstractRepository, session) -> str:
    ...
```

## Эмпирические правила для разных типов тестов
_Нужно стремиться к сквозному тесту на одну функцию_

К примеру тест может быть написан для HTTP API. Цель состоит в том, чтобы продемонстрировать, что функциональное
свойство работает и что все двужущие части "склеены" правильно.

_Нужно писать основную часть тестов для сервисной части_

Сквозные тесты предлагают хороший компромисс между охватом, временем выполнения и эффективностью. Каждый тест
охватывает один кодовый путь функционального свойства использует подделки (fakes) для ввода-вывода.
Это именно то место, где следует исчерпывающе охватить все крайние случаи и входы и выходы вашей бизнес-логики.

_Нужно поддерживать малое ядро тестов для предметной области_

Эти тесты точечный охват и являются более хрупкими, но при этом дают самую эффективную оценку. Не бойтесь удалять эти
тесты, если функциональность будет охвачена тестами в сервисном слое.

_Обработка ошибок должна рассматриваться как функциональное свойство_

В идеале приложение должно быть структурировано таким образом, чтобы все ошибки, которые всплывают в энтрипоинтах
(например, в эндпоинтах), обрабатывались одинаково. Из этого следую, что по каждому функциональному свойству нужно
тестировать только happy path и оставлять один сквозной тест для unhappy path (и разумеется, много юнит-тестов для 
unhappy path).
