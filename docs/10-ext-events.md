# Событийно-управляемая архитектура: использование событий для интеграции микросервисов

## Распределенный комок грязи

Есть альтернативный подход: декомпозиция системы на "существительные".

В этом случае, каждая "штука" в системе имеет собственную службу, которая предоставляет HTTP API. А каждый шаг
системы будет командой:

`ReserveStock` -> `ConfirmReservation` -> `DispatchGoods` -> `MakeCustomerVip`

Такой стиль архитектуры, где для каждой таблицы данных создают микросервисы, а HTTP API обрабатываются как CRUD-интерфейсы
для анемичных моделей - самый популярный изначальный подход к сервис-ориентированному дизайну.

**Хорошо работает с элементарными системами, но рискует быстро скатиться в распределенный комок грязи.**

## Альтернатива: временной устранение связанности при помощи асинхронного обмена сообщениями

Если думать "глаголами", а не "существительными", то можно получить подходящую связанность.

Вместо того, чтобы думать о системе для заказов и системе для партий товаров, мы думаем о системе для процессов
принятия и размещения заказов.

Каждая служба принимает внешние команды и инициирует события, записывая результат.
Соответственно, для это можно использовать обмен сообщениями вместо HTTP API.
Надо сделать так, чтобы сообщения `BatchQuantityChanged` поступали как внешние сообщения от вышестоящих систем и 
чтобы система публиковала события `Allocated`, которые будут прослушивать нижестоящие системы.

**Почему это лучше?**

- поскольку отдельные элементы системы могут отказывать, не затрагивая при этом ее остальные части, нам становится проще справлять с неэффективным поведением: мы по-прежнему можем принимать заказы, даже если служба размещения упала;
- мы уменьшаем степень связанности между системами: если нужно изменить порядок операций или ввести дополнительные этапы в процесс, то можно сделать это локально.

Для такого обмена сообщениями используются **брокер сообщений** (например, redis).
