# Unit of Work (UoW)

**Unit of Work** - это паттерн, который объединяет изменения в рамках одной бизнес-операции и сохраняет их в БД
одной транзакцией: либо все успешно фиксируется, либо все откатывается.
Отслеживает новый, измененные и удаленные сущности, а затем координирует `commit`/`rollback`.

## Зачем нужен

Например, при оформлении заказа, нужно одновременно:
- создать `Order`
- уменьшить остаток товара
- создать запись об оплате

Без UoW каждая операция может сохраниться отдельно - и при ошибке получится полуоформленный заказ.
С UoW изменения накапливаются, а потом выполняется единый `commit`.
```python
async with uow:
    order = Order.create(customer_id, items)
    await uow.orders.add(order)

    for item in items:
        product = await uow.products.get(item.product_id)
        product.reserve(item.quantity)

    await uow.commit()
```

Если внутри блока случится исключение, вызывается rollback(), и ни заказ, ни резерв товара не попадут в базу.

Типичный интерфейс
```python
class UnitOfWork:
    orders: OrderRepository
    products: ProductRepository

    async def commit(self) -> None: ...
    async def rollback(self) -> None: ...
```

Часто UoW владеет одной сессией/транзакцией БД, а все репозитории используют именно её.

## В Python и SQLAlchemy

В SQLAlchemy роль UoW во многом уже играет `Session`: она держит изменения объектов и при `commit` синхронизирует
их с БД в транзакционной границе. Поэтому отдельный класс `UnitOfWork` не потому, что ORM этого не умеет, а чтобы:
- не протаскивать `AsyncSession` в application/domain слои
- дать use-case'ам стабильный интерфейс
- централизовать управление транзакциями
- проще подменять доступ к данным в тестах

Не стоит механически оборачивать каждый repository в UoW: если приложение простое и Session уже аккуратно живёт на уровне одного запроса/use case, дополнительная абстракция может быть лишней. Суть паттерна — не «контейнер репозиториев», а единая атомарная граница изменений.

## Работает с Репозиторием

Паттерн UoW действует как единая входная точка в систему постоянного хранения данных и отслеживает загрузку объектов
и их последнее состояние.

Это дает три полезные вещи:
- стабильный моментальный снимок базы данных для работы, так что объекты, которые мы используем, не меняются на полпути
- способ сохранять все изменения сразу, благодаря чему мы не окажемся в состоянии несогласованности, если что-то пойдет не так
- простой API для обязанностей по обеспечению постоянства данных и удобное место для получения репозитория
