# Распределение обязанностей команд и запросов

**Большинство пользователей не собираются покупать мебель**

В примере компании из книги есть система, очень похожая на службу повторного размещения. В нагруженные дни могут
обрабатываться сотня заказов за час, для который есть большая грубая система размещения заказов.

Но в тот же самый день может быть 100 просмотров продукта в секунду. Каждый раз, когда кто-то посещает страницу 
продукта или его описания, нужно выяснять, есть ли продукт на складе и сколько времени потребуется для его доставки.

**Предметная область** - та же самая: партии товара, дата их прибытия и количество, которое все еще есть в наличии, но 
схема доступа очень отличается.

Например, клиенты не заметят, если запрос устарел на несколько секунд, но если служба размещения будет несогласованной,
то будет внесен беспорядок в заказы.

Можно воспользоваться преимуществом этой разницы, сделав операции чтения _согласованными в конечном счете_, чтобы 
заставить их работать лучше

Система будет представлять из себя две стороны: сторона записи и сторона чтения.

|                 | Чтение                          | Запись                                  |
|-----------------|---------------------------------|-----------------------------------------|
| Поведение       | Простое чтение                  | Сложная бизнес-логика                   |
| Кешируемость    | Хорошо подходит для кеширования | Непригодна для кеширования              |
| Согласованность | Может быть устаревшей           | Должна быть транзакционно согласованной |

# PRG и разделение команд и запросов

PRG (Post/Redirect/Get) - паттерн, по которому веб-точка принимает HTTP POST и отвечает перенаправлением, чтобы
увидеть результат. Например, можно принять POST на `/batches`, чтобы создать новую партию, перенаправить пользователя
на `/batch/123`, чтобы увидеть его только что созданную партию.

По факту PRG разделяет операции на фазы записи и чтения.

Этот метод является простым примером принципа разделения команд и запросов (command-query separation, CQS).

**Нужно следовать одному простому правилу:**

Функции должны либо изменять состояние, либо отвечать на вопросы. **Оба варианта сразу недопустимы.**

# SELECT N + 1 и другие соображения по поводу сообразительности

Проблема `SELECT N + 1` - проблема, связанная с ORM: при получении списка объектов ORM нередко выполняет начальный
запрос, чтобы получить все идентификаторы объектов, которые ему нужны, а затем выдает индивидуальные запросы для
каждого объекта, чтобы получить их атрибуты.
